# Travel Planner 2.0 — аудит перед изменениями

Базовая версия `e2a7cfd`. Пользовательские черновики для аудита не изменялись. Браузерные сценарии используют отдельные контексты и тестовые поездки.

| Контур | Текущее поведение и риск |
| --- | --- |
| Черновик | `TripPlannerDraft` читает `codoc/trip-planner/draft/v2`; primary visit находится в теле дня, дополнительные остановки — в `visits`. Часть обработчиков явно вызывает `persist`, часть меняет только React-состояние. |
| История | UI хранит три массива состояния; отдельные действия навигации не привязаны к стабильному ID дня. При переупорядочении индекс меняет смысл. |
| Аккаунт | `tripPayload` отправляется через PUT `/api/trips/:id`. Модель сервера поддерживает один `cityId` и один `accommodationId` на календарный день. Дополнительный город экспортируется как сегмент и как запись каталога городов. Потребуется отдельный договор об обратимом представлении visit-to-city и о ревизиях; серверную схему в этих фазах не меняем. |
| Карта | Планировщик, включая отели, использует Leaflet и растровые тайлы OSM. Векторный чанк отделён. Существующий PDF/снимок из редактора маршрутов использует отдельный адаптер. |
| Авто/пешком | POST `/api/journeys/routes/road` принимает именованные координаты и mode. Геометрия возвращается как `[longitude, latitude]`. Существующий редактор повторно использует любую непустую геометрию. |
| Поезда/самолёт | Прямой поезд берётся из расписания на дату, авиа — оценка. Дату, источник и устаревание нужно сделать видимыми на участке. |
| Прогулки | Принимаются только от текущего iframe, того же origin и с совпадающим channel. Схема проверяет порядок, геометрию и размеры; PDF конструктора выносит привязанные прогулки на отдельные листы. |
| Планирование дня | `cityVisitPlan` использует консервативное расписание и пропускает объекты без часов; оптимизация порядка по дорожной матрице пока отсутствует. |

## Порядок поставки

1. Phase 1 — редьюсер, безопасное автосохранение, стабильная идентичность, ключи геометрии, рабочее пространство.
2. Phase 2 — чистое расписание, сетевая матрица и предпросмотр оптимизации с проверкой жёстких ограничений.
3. Phase 3 — состояния поставщиков, часовые пояса, неоднородный круговой экспорт.
4. Phase 4 — адаптивность, доступность, производительность, проверка PDF и отдельный флаг запуска.
